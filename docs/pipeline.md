# Sony 创意外观的像素路径：1024×18 表与 0x7806 曲线

> 研究记录，按时间顺序保留了当时的推断和更正。文中提到的测试导出、`c1_test/`、`photo_test/`、`chart/` 测量结果、REA 证据和反编译文件属于原研究工作区，不在本仓库中；脚本名和用法以仓库根目录 README 为准。

日期：2026-10-16。目标：Imaging Edge Edit 4.0.00.10312，arm64 切片 SHA-256 `a03b2449…5da442`。工具：REA 6.5.0（Ghidra 12.1.4 后端），Unicorn 2.1.4。

**结论**：两部分数据在像素层面怎样使用，现已全部恢复，并用原始 ARM64 指令逐位验证（52/52 例，0 字节差异）。1024×18 表用于 `ZcTaskLinearMatrix16`：按色相查表，做 3×3 线性矩阵，再加一个平方项。0x7805/0x7806 用于 `ZcTaskMainGamma`，是一条逐通道的 1D 曲线，把 14 bit 线性值映射为 14 bit 编码值。两者在管线中相邻，前者先执行。

**更新（第 8 节）**：0x7841–0x7848 的实际消费者是 `ZcTaskRGB2YCC`。它在色差空间按象限做剪切和增益，同样已逐位验证（141/141 例）。之前怀疑的 129×129 二维表虽然会被构建，但静态扫描找不到任何读取它的代码。

还没完成：0x780c–0x780e，以及 YCC 域之后的 YGamma、3DLut、HueSaturation 等阶段（见第 6 节）。所以当前实现**还不是完整的 FL2/FL3 外观**。

## 1. 管线顺序（RTTI 类名）

`sony_zhacai::ZcTask*` 类的 RTTI 名称保留在二进制中。按 vtable 找到构造函数，再找到构建管线的函数 `0x1000b85e0`（RAW 路径），得到顺序如下：

```
TileDiv → RawNR → Demosaic* → TrinityLPF → [Vatr] → [GeoCorrection] → SSCS
→ LinearMatrix16   ← 1024×18 表（存在 0x780f 时；否则 LinearMatrix 使用旧 0x7800 矩阵）
→ MainGamma        ← 0x7805/0x7806 曲线
→ RGB2YCC → [AreaComp] → ChromaSuppress → Sharpness → YGamma → [3DLut] → [HueSaturation]
→ [YNR] → [Spica] → YCC2RGB → [Marble] → [Effect] → [ToneCurve] → [ShadeCorrection]
```

管线里的 SIMD 变体由 `0x10004f5a8` 决定是否启用；该函数在此版本中恒定返回 0，因此实际运行的是普通实现（`LinearMatrix16::Process = 0x1000acdd4`）。

## 2. LinearMatrix16（0x1000acdd4 → 0x1000abaf0 / 0x1000abe38 / 0x1000ac6b0）

输入为三平面 float、14 bit 线性 RGB（0..16383）。逐像素处理：

1. **低通**：对每个平面做水平 `[1 8 14 8 1]/32` 滤波，边缘有专门的系数（左侧 `23,8,1` / `9,14,8,1`，右侧对称）。
2. **色相**：先算 `Y = (109R + 366G + 37B)/512`（BT.709 系数，double 精度）；再取 `a = R−Y`、`b = B−Y`，按八分象限查 `0x100234730` 的 512 项 atan 表，得到 `hue ∈ [0,1024)`，1024 = 360°。默认用低通后的平面计算（控制字 `0x91998 = 0x9199a = 1`）；`0x9199c = 1` 时 a×0.875、b×0.5（本批外观均为 0）。
3. **查表**：`i = min(trunc(hue), 1023)`，取第 i 行的 18 个 float。前 9 个为矩阵 B，后 9 个为矩阵 N（行优先）。
4. **混合**（每个输出通道 k 独立计算）：

```
lin_k = B_k · (r, g, b)                     # FMA 链：B2*b + (B1*g + B0*r)
q_k   = N_k · (r², g², b²) / 16384
out_k = lin_k                  若 q_k < 0
      = lin_k + q_k − thr_k    若 q_k ≥ thr_k
      = lin_k + q_k + thr_k    若 q_k ≤ −thr_k
      = lin_k                  其他
out_k = clamp(out_k, 0, 16383)
```

`thr` 位于外观结构 `+0x91bac/b0/b4`，对应 blob 尾部的三个 /32 值，本文件 12 种外观中均为 0。所以实际效果是：**平方项只在为正时叠加**。控制字 `0x91bba = 0` 时，改走 `0x1000ac1b4`，只计算线性项。

由此可以读出它的性质：在本批数据（T=1）中 `B + N = I`，且 B 每行之和为 1，所以中性灰保持不变。暗部效果约等于 B，越接近 16383 越趋向恒等，等于一个随亮度渐弱的色相分段矩阵。

**相机修正矩阵**：表构建器（0x1000d4288）会查询 `DAT_1002f7450` 处的数据库，用来叠加机型修正。扫描全部 `__TEXT` 的 adrp+ldr/str/stp/add 指令后发现，这个全局变量只被读取，以及在析构时清零，从未被赋值。因此运行时查询恒返回 NULL，之前验证过的"单位修正矩阵"分支就是 Edit 实际走的分支。

**output_mode / param8**：四个静态矩阵中，`mode1/param8=0` 正是 sRGB→AdobeRGB 线性矩阵（0.7152 0.2848 0 / 0 1 0 / 0 0.0412 0.9588），`mode0/param8≠0` 是它的逆。可以推断：mode 是输出色彩空间，param8 表示工作色域为 AdobeRGB。本文件记录的是 sRGB（ExifIFD ColorSpace = sRGB），所以导出 sRGB 时应为 `mode0/param8=0`，即不使用静态矩阵，LM16 工作在 **sRGB 原色的线性空间**。这一点是推断，还没有用运行时验证。

## 3. MainGamma（0x1000c7774 构建，0x1000e96a0 应用）

查表数据来源：`FUN_1000a71fc` 读取 0x7805/0x7806（各 128 个 int32），放在外观结构 `+0x5d8/+0x7d8`。主 SR2SubIFD 中 0x7807 = 128 给出节点数，0x7808 = 1、0x780a = 0 设置标志 `+0x1d0 = 0x11`，选用新曲线路径。

构建：

```
for i in 1..32767:  x = i*128                         # 0x7805 的单位 = 14bit 线性 × 128
    y = 分段线性插值(0x7805 → 0x7806)                   # float32: (y0−y1)*(x1−x)/(x1−x0)+y1, 截断
    若有二级表: y = trunc(fma(frac/64, t[k+1]−t[k], t[k]))，其中 k = y>>8, frac = (y>>2) − 64k
    LUT[i] = y >> 4                                     # 14 bit 编码输出
LUT[−m] = −LUT[m−1]                                     # 负半轴镜像
```

应用：`out = trunc(fma(LUT[i+1]−LUT[i], v−floor(v), LUT[i]))`，其中 `i = trunc(v)`，结果为 int16，三个通道独立。

二级表：对比度、高光、阴影都为 0 时，旧路径（`PTR_DAT_1002c4b30[对比度+3]`）的第 3 项是空指针，新路径（`0x10011e174`，37 条曲线族，按 `对比度±高光/阴影×0.2+18` 插值）的第 18 条是恒等曲线 64·i。两条路径在默认值下都等价于直接使用 0x7806/16。

## 5. 数据特征（仅用本实现计算，非 Sony 成片）

0x7806 曲线：横轴为占 14 bit 满量程的比例（×0.18×2^EV），纵轴为输出 0..1。

| 外观 | −6 | −4 | −2 | −1 | 0 | +1 |
| --- | --- | --- | --- | --- | --- | --- |
| Standard | 0.046 | 0.176 | 0.489 | 0.697 | 0.872 | 0.974 |
| FL2 | 0.051 | 0.204 | 0.638 | 0.798 | 0.901 | 0.983 |
| FL3 | 0.056 | 0.225 | 0.624 | 0.806 | 0.926 | 0.986 |

线性 sRGB 色相扫描（饱和度 0.5）的趋势：FL2 把青色推向蓝色（180°→204°），把红色推向橙色（0°→16°），黄色和蓝色的饱和度提高到约 0.6–0.7；FL3 整体降低饱和度（0.41–0.55）。这只描述 LM16 一个阶段，不等于完整成片效果。

## 8. 0x7841–0x7848：RGB2YCC 中的色差剪切与增益

### 8.1 数据流

| 标签 | 位置 | 本文件取值（ST） |
| --- | --- | --- |
| 0x7841 | 主 SR2SubIFD → 外观结构 `+0xddc` | −51 −191 −269 −325 940 774 972 1126 |
| 0x7842 | 外观 IFD → `+0xdec`（基准组） | −51 −207 −269 −184 1126 748 1052 1126 |
| 0x7843–0x7846 | 外观 IFD → `+0xdfc/+0xe0c/+0xe1c/+0xe2c`（增量组） | 0x7843 = 0x7846 = 0；0x7844、0x7845 随外观而异 |
| 0x7847 / 0x7848 | 主 SR2SubIFD → `+0xe3c/+0xe44`（4 个混合权重，单位 1/1024） | 都是 `0 1024 0 0` |

解析时（`FUN_1000a74bc`，前提是解析对象 `+0x19c == 2`），六组数组的第 4–7 项（增益）都要除以 `0x1002e6950[sat+9]`，其中 sat 是解析对象 `+0x200` 记录的饱和度，取值 −9..9，对应因子 0.43…1.56。本文件饱和度为 0，因子 1.0，相当于不变。

渲染时，`ZcTaskRGB2YCC::Process`（0x1000ee0cc）调用 `FUN_1000ed9b4`，按开发参数 `+0x1e8` 的模式 m 取出有效的 8 个参数 p：

| m | p |
| --- | --- |
| 1 | 若字节 `+0x1c` 置位则直接用 0x7841；否则为 0x7842 + Σ w0x7848[i]·组[i] >> 10 |
| 2–6、0、≥0xe | 0x7842 + 0x7844 |
| 7–10 | 0x7842 + 0x7845 |
| 0xb | 0x7842 + 0x7843 |
| 0xc | 0x7842 + 0x7846（满足白电平条件时），否则同 0xd |
| 0xd | 0x7842 + Σ w0x7847[i]·组[i] >> 10 |

本文件权重为 `0 1024 0 0`，所以除 7–10、0xb、0xc 以外，所有模式都得到 **0x7842 + 0x7844**。四个增量组配合按场景记录的混合权重，形态很像"按光源/白平衡模式分组的色差修正"，但 `+0x1e8` 的语义尚未确认，这只是推断。

### 8.2 像素公式（输入为 MainGamma 输出的 int16 R、G、B）

```
Y   = ((19·128)·R + (38·128)·G + (7·128)·B) >> 13       # 系数来自 0x7801 = 19 38 7（≈BT.601）
rg  = R − G,  bg = B − G                                 # float32
sh(v) = sign-extend9((v>>2) & 0x1ff) / 256               # 剪切
gn(v) = ((v>>3) & 0xff) / 64                             # 增益
Cb' = fma(sh(rg<0 ? p3 : p1), rg, bg)
Cr' = fma(sh(bg<0 ? p2 : p0), bg, rg)
Cr' = Cr'·0.5·gn(Cr'<0 ? p7 : p5)
Cb' = Cb'·0.5·gn(Cb'<0 ? p6 : p4)
若开发参数 +0x248 == 0：Cr'、Cb' 限制在 [−8192, 8191]
输出平面 0 = Y，平面 1 = clamp_u16(trunc(Cr' + 32768))，平面 2 = clamp_u16(trunc(Cb' + 32768))
```

`ZcTaskYCC2RGB`（0x1000fb500）是固定的 BT.601 逆变换（1/10000 整数，向零截断，结果限制在 0..16383）：

```
R = Y + 1.4020·Cr,  G = Y − 0.7141·Cr − 0.3441·Cb,  B = Y + 1.7720·Cb
```

所以外观对色彩的作用全部集中在 RGB2YCC 的四象限剪切和增益里：四个色差象限各有自己的"色相旋转"（剪切）和"饱和度"（增益）。

### 8.3 129×129 二维表（可能是死代码）

`FUN_1000d5700` 用同一套数组构建 `render+0x49910` 的 129×129 网格（`FUN_1000bee38` → `FUN_1000bef10` 选参数，选择规则与 `FUN_1000ed9b4` 相同；`FUN_1000bf488` 做与 8.2 等价的 double 精度象限变换；`FUN_1000bf670` 还会按 0x784c–0x784f 等参数向 4 个中心收拢）。

扫描整个 `__TEXT` 的 adrp/add/ldr/ldp/movz+movk 指令组合后，`render+0x49910` 只出现在写入点 0x1000d5720、分配处和析构处。数据库中的 3D LUT 构建（`FUN_1000d2c6c` 用 `+0x49900/+0x49918`）、`ZcTask3DLut`（`+0x49920`）和各个 YCC 任务都不读它。因此没有对它做移植和逐位验证。若之后在运行时观察到读取，需要补上这部分。

### 9.2 YGamma（始终运行）

LUT 构建 `FUN_1000c7120`：
1. 基础曲线取自外观 `+0x9dc`（512 点；新路径下是恒等 i·4）。若开发参数 `+0x248` 非零，先按 `+0xf8a/c/e` 重映射。
2. 应用 0x780c/0x780d 高光拐点。
3. 用 `+0x44` 对比度在两张预置表（`+0x1082/+0x1482`）之间混合，`fma(k, 表−x, x)·曲线/x + 0.5`。
4. `FUN_1000c6e28` 把曲线分成四段重采样（参数 `+0x50/+0x54`），索引用 floor，小数部分用 FMA 计算。
5. 512 → 2048 → 32768 点线性展开，负半轴置 0。

逐像素（`0x1000feb68`）：`v = LUT[Y]`；`v' = (v>s2 ? (v−s2)·512 : 0)·(1/(512−dev2b0+q)) − off`；`out = clamp(fma(v', gain, off), 0, 16383)`。其中 s2、q 来自开发参数 `+0x2ac`；默认值下 `out = gain·LUT[Y]`。

`+0x44/+0x50/+0x54` 只在机型代号小于 2 时取用户的对比度、高光、阴影；新机型这一项为 0，这些调整改在 MainGamma 的曲线族中完成（第 3 节）。

### 9.3 ChromaSuppress（始终运行）

1. 由外观 `+0xf00…+0xf0e` 和格式 ID（`+0x2c`，某些 ID 改用内置表 0x100243f50/0x100244000/0x1002440b0）得到暗部阈值与亮部阈值。按曝光 `render+0xc/300`（EV）在 −2..−1、−1..0 两段之间插值。
2. 亮部阈值依次经过反线性化表 `+0x89962` → `+0x69962` → MainGamma LUT → YGamma LUT 映射到 Y 域；暗部阈值为 `亮部值·f0e/f06`。
3. 逐像素：`f = 255 − (Y 越界量·斜率 >> 12)`，限制在 0..255。色差按 `(C−32768)·f/256`（向零截断）缩放，Y 的负值置 0。

这一级只在暗部和高光压低色度，不承载外观的色彩差异，所用外观字段在 12 种外观之间也没有区别。

### 9.4 HueSaturation（仅当 +0x204 或 +0x1fc 非零时加入管线）

这是用户的色相和饱和度滑块（设置键 0x8019 / 0x8016），不使用外观数据。
- 色相每档旋转 0.35°（负方向）或 0.7°（正方向）。角度用 `FUN_1000e53ac` 的多项式 atan2 计算（double，含 FMA），再查运行时生成的 512 项 sin 表（`FUN_1000e56e0`：`float(sin(i·2π/512))`）。
- 饱和度为 `1 + 0.01·s`。

在模拟器中，这张 sin 表用 Python 的 `math.sin` 按相同公式预先填入；macOS 上它与程序共用同一个 libm，但这一点没有单独验证。

### 9.5 3DLut（仅当 +0x248 非零时加入）

逐像素（`0x10013db80`）：
1. 先把 Cr/Cb 还原为差值轴：`A = fma(Cr', 1.401988, Cb'·3.7e-5)`，`B = fma(Cr', 0.000135, Cb'·1.771978)`，限幅后经过 1D shaper（LUT 对象 `+0x48`）。
2. 按 Y（`>>(14−f2c)`）、A、B（`>>(16−f30)`）做 8 角整数权重的三线性插值；权重之和为 512，节点数据为每个节点 24 个 int16 的"立方体"。
3. 输出 `Cr = fma(A, 0.713273, −1.5e-5·B)`，`Cb = fma(B, 0.564341, −5.4e-5·A)`。

已移植并验证的只是**应用部分**。LUT 的内容来自 `render+0x49920` 的 "main 3D-LUT"：`FUN_1000d584c` → `FUN_1000d2c6c` 由 "beginning 3D-LUT"（`FUN_1000c295c`，基于 gamma 对象）构建，并可叠加 `render+0x49918` 的对象表。这条构建链还没有分析。

### 9.6 默认会运行哪些阶段

开发参数来自设置存储（`FUN_1000aac90`：键 0x8002 → `+0x1e8` 模式，0x8016 → `+0x1fc`，0x8019 → `+0x204`，0x8026 → `+0x248`）。默认值由另一条初始化路径写入，尚未静态确定。

从语义推断：滑块默认为 0，此时 HueSaturation 不加入管线；`+0x248`（3D LUT 开关，同时让 RGB2YCC 不再做 ±8192 限幅）的默认值需要运行时确认。

### 9.7 目前可串联的外观链路（sRGB 输出、默认参数）

```
线性 sRGB 14bit → LinearMatrix16(0x780f) → MainGamma(0x7806) → RGB2YCC(0x7842+0x7844, 0x7801)
→ ChromaSuppress → [Sharpness] → YGamma(0x780c/d 拐点, 0x780e 增益) → [3DLut] → YCC2RGB
```

12 种外观在这些阶段中**所有因外观而异的数据都已有逐位验证的实现**（0x780f、0x7806、0x7842/0x7844/0x7845、0x780c–0x780e）。仍缺：Sharpness/YNR/Spica 等空间滤波（不承载色彩风格）、3D LUT 内容的构建、Demosaic/SSCS 之前的相机色彩、开发参数默认值，以及与 Sony 官方成片的端到端对照。

证据：`../rea/phase5/evidence/`、`../rea/phase5/evidence_bundle.json`、`../rea/phase5/decompiled/`。

## 10. 端到端对照：与 Imaging Edge 导出的 16-bit TIFF 比较（2026-10-16）

### 10.1 参考图与识别

用户导出的 `reference/DSC03591.TIF`、`DSC03591fl.TIF`、`DSC03591fl2.TIF`（4672×7008，16 bit，DRO 已关，Edit 4.0.00.10312）没有记录外观名称，所以用数据来识别。在 12 种外观的所有组合中，(fl2 − fl) 与本实现的 (FL3 − FL2) 吻合度最高（误差 0.94，第二名 2.23），由此确定 fl = **FL2**、fl2 = **FL3**、无后缀 = **ST**。`render_reference/` 中用符号链接按规范名指向这三个文件。

### 10.2 方法

运行 `compare_reference.py`：
- 前端用 LibRaw 0.22（AHD，拍摄时白平衡 2653/1024/1416，相机 → 线性 sRGB）。
- 外观链：LM16 → MainGamma → RGB2YCC → ChromaSuppress（近似）→ YGamma → YCC2RGB。
- 输出 8× 盒式缩小后比较，单位为 8-bit 级。
- 曝光只用 ST 拟合，**k = 0.48**，FL2/FL3 原样沿用。

### 10.3 结果

| 指标 | ST | FL2 | FL3 |
| --- | --- | --- | --- |
| 绝对 MAE | 6.40 | 4.71 | 5.11 |
| 偏差 R/G/B | +3.9/+1.2/−8.7 | +2.3/+0.6/−3.7 | +2.9/+0.1/−4.3 |
| 外观差残差（相对 ST） | — | 2.91（Sony 外观差 14.4，相关 0.957） | 2.89（Sony 14.9，相关 0.953） |

外观带来的变化约 80% 被复现。消融（把 FL2 的某一阶段换成 ST 的，看误差变化）：

| 换成 ST 的阶段 | 本模型内效应量 | 对 Sony 的 MAE |
| --- | --- | --- |
| MainGamma（0x7806） | 15.1 | 4.7 → **17.8** |
| RGB2YCC 参数（0x784x） | 8.9 | → 12.4 |
| YGamma（0x780c–e） | 2.7 | → 5.3 |
| LM16 表（0x780f） | 2.1 | → 4.6（基本不变） |

所以色调曲线和色差剪切/增益承载了外观的大部分。另外，去掉 LM16 平方项会让 FL2 误差从 4.71 变成 5.16，说明平方项的模型方向正确。

### 10.4 交叉验证

- 主 IFD 的 0x7841（相机记录的当前实际参数）**正好等于** ST 的 0x7842 + 0x7844，独立证实了模式 1 和权重 `0 1024 0 0` 的选择规则。
- 去掉 ST 的 YGamma 增益 1.0547，ST 误差从 6.40 升到 8.83，证实 0x780e 的用法。
- 换用其他模式（7/0xb）或直接用 0x7841：ST 改善时 FL2/FL3 会变差，三者无法同时改善，因此不成立。

### 10.5 剩余误差

1. **共同的蓝色偏差约 −4 到 −7**，不随亮度变化，来自前端：白平衡应用、相机矩阵或曝光，LibRaw 与 Sony 的 Demosaic/SSCS 不同。
2. **ST 在明亮偏黄区域额外缺蓝，最多 −16 到 −35**：本实现的 ST 天空明显比 Sony 饱和。把 ChromaSuppress 阈值从 16383 降到约 14000 后，三种外观同步改善（ST 6.40→5.95，FL2 4.71→4.56，FL3 5.11→4.94），说明 Sony 的高光色度抑制介入得更早。精确阈值已在 §10.6 还原（15356），改善很小。但只调阈值不能解释全部 ST 差异。另一个候选是默认开启的 3DLut（"beginning/creative 3D-LUT"），以及 `+0x248` 带来的 RGB2YCC 限幅差异，都需要继续追踪。
3. 锐化、降噪、镜头校正都没有实现；8× 缩小已经削弱了它们的影响。

产物：`../render_output/compare_report.json`、`compare_{ST,FL2,FL3}.png`（Sony | 本实现 | 4× 放大差值）、`montage_sony_vs_ours.png`。

### 10.6 ChromaSuppress 精确阈值（FUN_1000c2618 / c2690 / c2204，2026-10-16）

`FUN_1000d50f8`（在 MainGamma LUT 和 YGamma LUT 建好之后、由 `FUN_1000d3048` 调用）生成两张逆查表：

- `render+0x69962` = `FUN_1000c2618(gammaObj, render+0x18f6, …)`：MainGamma LUT（65536 项、以 0x8000 为零点）的单调逆表。对 v = 0..0x7fff，从上一次的位置 k（初值 0x8000）向后找第一个满足 `lut[k+1] >= v` 的 k，写 `out[0x8000+v] = k−0x8000`、`out[0x8000−v] = −(k−0x8000)`（奇对称，元素 0 不写）。
- `render+0x89962` = `FUN_1000c2690(gammaObj, render+0x218fc, …)`：YGamma LUT（**不含** 0x780e 增益）正半轴的逆表，只有 16384 项，同样的查找，结果 `min(k,0x17fff)−0x8000`。
- `render+0x18ee = (short)(int)(exp2(render+0xc / 300) · 64)`，`render+0xc` = `dev+0x1f8`（设置 0x8018，曝光补偿，单位 1/300 EV）。曝光为 0 时等于 64，即 d0 = 1.0。
- `FUN_1000c2204` 用同一链计算 gammaObj+0x40：`YG[MG[min(invMG[invYG[f06]]·0x18ee >> 6, 0x7fff)]]`。ChromaSuppress（0x1000e6da0）的高光阈值 w12 是同一条链（只是乘法改为 double）。

含义：阈值 `0x787f[0] = 15360` 定义在 **YGamma 输出域**，先反推到线性，乘曝光系数，再正向映射回来。所以曝光为 0 时阈值约等于 15360 本身（ST/FL2/FL3 都是 **15356**），而之前的近似是把 15360 当线性值，正向经过两条曲线，得到 16383，等于没有开启抑制。负曝光时阈值和斜率随之变化（例如 −1 EV：w12 12816、斜率 374/1024）。

验证：`verify_cs_tables.py`，用真实外观（Standard/FL2/FL3/VV2/IN/SH/BW）的 LUT 和随机曲线（含非单调），两张逆表和阈值函数 **70/70 逐位一致**（`verify_cs_tables_report.json`）。`sony_render.Look.chroma_params(ev)` 现在走这条精确链。

端到端重跑（scale 8，曝光仍为 ST 拟合的 0.48）：

| 指标 | ST | FL2 | FL3 |
| --- | --- | --- | --- |
| 绝对 MAE（近似阈值 16383） | 6.40 | 4.71 | 5.11 |
| 绝对 MAE（精确阈值 15356） | **6.35** | **4.66** | **5.04** |
| 外观差残差 | — | 2.90（相关 0.957） | 2.91（相关 0.953） |

精确阈值带来的改善是真实的，但幅度小。之前扫阈值时 14000 更好（ST 5.95），但那个值不是 Sony 的设定，只是在用 ChromaSuppress 去补偿别处的误差。因此 §10.5 第 2 条里 ST 亮黄天空缺蓝的问题**不能**归因于 ChromaSuppress 阈值。剩下的候选按可能性排序：默认开启的 3DLut（dev+0x248 / "beginning 3D-LUT"）、前端（Sony 的 SSCS/相机矩阵与 LibRaw 不同，蓝通道偏差在三种外观里都有），以及 RGB2YCC 的限幅路径。

### 10.7 导出时实际生效的开关（Edit 写回 ARW 的设置 IFD，2026-10-16）

用 Edit 导出后，根目录的 `DSC03591.ARW` 末尾多了 1630 字节（原始文件见 `reference/DSC03591.ARW`，SHA `cfb421…`），预览 JPEG 也被重写了。末尾是一个小 TIFF 结构：`0xd001` 指向两个 IFD，分别是"当前"和"初始"设置。条目 ID 就是 `FUN_1000aac90` 读取的设置 ID，序列化代码在 0x10010ebxx（类型 3 = SHORT，9 = SLONG）。

| 设置 | 映射 | 当前 / 初始 | 含义 |
| --- | --- | --- | --- |
| 0x8026 | dev+0x248 | 0 / 0 | **3DLut 关闭**；render+0x60 = 0，ChromaSuppress 走 c2204 分支（§10.6） |
| 0x8016 / 0x8019 | dev+0x1fc / +0x204 | 0 / 0 | **HueSaturation 关闭** |
| 0x8002 | dev+0x1e8 | 1 / 1 | RGB2YCC 模式 1（与 §8 推断一致） |
| 0x8018 | dev+0x1f8 | 0 | 曝光补偿 0 → render+0x18ee = 64 |
| 0x901b / 0x9017 / 0x9018 | dev+0x2bc / +0x2b0 / +0x2ac | 0 | YGamma 档位 0、偏移项 0（与渲染器一致） |
| 0x801e | dev+0x218 | 1 / 0 | 加入降噪任务（`FUN_1000b83e8`，dev+0x22c ≥ 1 时还有 YNR） |
| 0x8022 | dev+0x238 | 1 / 0 | 加入 Vatr 任务（推测是镜头校正） |
| 0x8000 | dev+0x1e0 | 1 / 2 | 传给解码器取外观数据的虚函数（vtable+0xe0）的参数 |

另外 **Spica**（`ZcTaskSpica`，处理函数 0x100100b60，位于 YNR 之后、YCC2RGB 之前）在 `srsettings0000.tbl` 能加载时启用（全局指针 0x1002f7468，由 0x1000ffc30 → 0x1000e4cb0 读文件）。这个文件在 Edit.app/Contents/Resources 里，所以 Spica 会运行。它只处理 Y：7×7 邻域分类后，用每类一组系数（0x68 字节）滤波，输出 `Y + (滤波 − Y)·强度`。这是类似 RAISR 的细节增强，局部均值基本不变。

结论：
- 3DLut 和 HueSaturation 在这三张导出图里都没有运行，所以不是 ST 亮黄天空缺蓝的原因。
- 降噪、Spica、Vatr 都是空间处理。径向检查显示，本实现与 Sony 的亮度比从中心的 0.999 到边缘的 0.982，只有约 1.7% 的暗角差异。颜色偏差（中心 B −14，边缘 B −5）跟画面内容有关，和半径无关。
- 剩余误差集中在**前端颜色**：白平衡、相机矩阵、SSCS，以及曝光与黑电平。这是下一步要还原的部分。

### 10.8 Sony 前端：黑电平、白平衡、缩放，没有相机矩阵（2026-10-16）

用 REA 追到的前端（phase8）：

- **ZcTaskDemosaic**（处理函数 0x100138ac8）在插值前对每个 CFA 样本做 `out = (int)(look[0x40] · 2⁻¹⁹ · gain[cfa] · (raw − look[0x38+cfa]))`，结果限幅到 int16，按 double 从左到右计算。索引是 `(x&1) | (y&1)<<1`。
  - look+0x38 = SR2SubIFD **0x7310** BlackLevel（512×4）
  - look+0x40 = **0x7311**（本文件为 256）
  - 标签到 look 偏移的映射从解析代码 0x1000a2xxx–0x1000a5xxx 自动提取。0x7313 → +0x4a，0x7800 → +0x9c，0x7801 → +0x1ca。
- **白平衡增益**来自 `FUN_10013c4b0`。白平衡模式 dev+0x1e8（设置 0x8002）= 1 表示"拍摄时设置"，取 0x7313 WB_RGGBLevels 的 R/G/B = 2653/1024/1416。之后 `FUN_10013c0bc` 用 look+0xf46… 的色温节点表插值出色温，`FUN_10013c29c` 按色调偏移 dev+0x1f0 修正，偏移为 0 时不变。再乘 `exp2(EV/300)` 和 dev+0x1f4 对应的 R/B 系数，当前设置下都是 1。模式 2–0xd 分别对应色温和各预设光源。
- 因此 G 通道 = 0.5·(raw−512)，R、B 分别乘 1.295 和 0.691。**曝光不再需要拟合**；之前用 LibRaw 拟合出的 0.48–0.50 正是这个 0.5。
- **没有相机矩阵**：有 0x780f 时（look+0x1c2 ≠ 0）构建器只插入 LinearMatrix16，所以 0x780f 表直接作用在白平衡后的**相机原生 RGB**上。每个外观各自的 **0x7800**（例如 FL2 `960 17 47 / 46 1091 -113 / -406 -184 1614`）由 `FUN_1000d4cfc` 与静态矩阵相乘后写入 render+0x18a4，只有非 16 位的 LinearMatrix 和 ChromaSuppress 的 3DLut 分支使用它，这里不生效。
- SSCS（0x1000f0e14）在 Bayer 计数权重下把接近饱和的高光压向亮度。本图线性最大值是 11492，基本不触发，所以没有移植。

实现：`sony_frontend.py`（`wb_gains`、`cfa_scale`、`block_average`），`sony_render.front_end_sony(scale)`。插值部分用 s×s 块内按 CFA 通道取平均代替，在缩小比较里等价于 box(demosaic)。`compare_reference.py --front sony`（默认）不再拟合曝光，`--front libraw` 保留旧路径。

端到端结果（scale 8，曝光固定为 1.0，没有任何拟合参数）：

| 指标 | ST | FL2 | FL3 |
| --- | --- | --- | --- |
| 绝对 MAE（LibRaw sRGB，拟合曝光） | 6.35 | 4.66 | 5.04 |
| 绝对 MAE（Sony 前端，无拟合） | **3.56** | **3.74** | **3.89** |
| 偏差 R/G/B | −0.6/−0.7/−0.9 | −0.9/−0.9/−1.0 | −0.9/−1.0/−1.0 |
| 外观差残差 | — | **1.02**（相关 0.985） | **0.97**（相关 0.982） |

之前三种外观共同的蓝色偏差（−4 到 −9）和 ST 天空缺蓝都消失了，**原因是前端多乘了一次相机→sRGB 矩阵**。外观带来的变化现在复现到约 93%。

剩余误差：
1. 和局部梯度的相关系数是 0.59，主要是空间处理：Sharpness、Spica、YNR、Demosaic 插值。对齐已检查，最佳平移是 (0, 0)。再缩小 4 倍后 MAE 约 2.6。
2. 影调上暗部偏亮约 +1.5、中间调偏暗约 −2.2。诊断拟合 `a·x + b` 得到 b = 0、a ≈ 1.02，也就是还缺约 2% 的增益。候选阶段：**AreaComp**（解码器机型代码 > 0x3232 且 `&0xf000 == 0x3000` 时插入，位于 RGB2YCC 之后）、**Marble**（dev+0x218 = 1 且 look+0x109c ≠ 0 时插入）、ToneCurve。下一步要确认它们是否运行，并移植。

### 10.9 YCC2RGB 前后的条件阶段：AreaComp、Marble、ToneCurve、ShadeCorrection、Effect（2026-10-16，REA phase9）

先确定构建器 `FUN_1000b85e0` 中各条件在本文件上的取值：

- **ARW 格式代码** = 解码器 `ZcARW` 的 vtable+0x58，返回 `ZcARW+0x50`。它由 0xb000 FileFormat 换算（0x1000a2860 起）：首字节 6（ARW 6.0），后两字节为 0，得到 **0x3600**。（`ZcARW` 的 vtable 位于 0x1002c3c80，从 RTTI `N11sony_zhacai5ZcARWE` 找到。）
- **外观编号** look+0x34 = look+0x20，来自外观 IFD 的名称字符串 0x7770，经 `FUN_10009ee90` 查表 0x1002c31e8 得到：Standard 2、Vivid 4、Neutral 7、Portrait 8、BW 0x10、Sepia 0x11、FL 0x12、VV2 0x13、IN 0x14、SH 0x15、FL2 0x16、FL3 0x17。

| 阶段 | 条件 | 本图 | 结论 |
| --- | --- | --- | --- |
| AreaComp（RGB2YCC 之后） | 格式代码 > 0x3232，且 `&0xf000 == 0x3000`，且 ≠ 0x3fff | 0x3600 | **运行**，已移植，逐位一致 |
| Marble（YCC2RGB 之后） | `(dev+0x218 == 1 且 look+0x109c ≠ 0)` 或 dev+0x2c0 ≠ 0 | 0x801e = 1，0x794a = 1，0x901c（清晰度）= 10 | **运行**，已移植（§10.16） |
| Effect | `look+0x34 & ~1 == 0x10`（BW/Sepia） | 2 / 0x16 / 0x17 | 本图不运行；BW/SE 运行，已移植（§10.14） |
| ToneCurve | `FUN_1000aed14(dev)`：4 条曲线全为恒等时跳过。曲线点 x 来自 0x9000+k，y 来自 0x9004+k（/511） | 全部是 `[0, 511]` | 不运行 |
| ShadeCorrection | dev+0x17c 或 dev+0x180 ≠ 0。它们由 `FUN_1000c4ee8(dev+0x170, 0x8030, 0x8031, 0x8032)` 写入，函数用 cos⁴ 规律生成暗角补偿曲线 | 80 / 0 / 0 | 不运行 |

**AreaComp**（处理函数 0x1000b3aec，参数来自 `FUN_1000b3db8` → `FUN_1000b3ee8`，条件是格式代码 > 0x33ff 且有 0x780f）：
- 只修改色度平面 1、2（Cr′、Cb′，以 0x8000 为中心）。
- 用 4 条边界距离判断是否落在区域内，每条是 `fmadd(c1+b, k1, (c0+a)·k0)`，负值截为 0。取 `m = min(min(d3,d2), min(d1,d0))`，输出在 double 中计算 `a + 32768 + (float)(m·k)` 后截断。
- 常量：区域中心 (0,0) 和 (−72,54)；法向量 (0.25, 0.109375)、(−0.53125, −0.828125)、(−0.765625, 0.359375)、(−0.328125, 0.9375)；位移系数 (0.234375, 0.28125)。Portrait 有另一组常量。
- 作用区域只是中性灰附近的一个小楔形（平面 1 约 20…69、平面 2 约 −61…−17），最多移动 2 个单位，满量程是 ±32768。
- `verify_area_comp.py`：4 种外观 × 3 组输入，**12/12 逐位一致**，密集用例中约 700 个样本被修改。已接入 `sony_render.Look`；端到端 MAE 在小数点后三位不变。

**Marble**（处理函数 0x100126f0c，约 1500 行，另有 11 个子函数共约 1500 行）：
- 先把输出 RGB 转成自己的 YCC：Y = (0xb44·R + 0xdc3·G + 0x271·B) >> 11，再加 0x1000。
- 然后对 Y 和半宽色度做 8×8（或 4×4）块平均金字塔，在小尺度上处理后放大回去，最后用 `FUN_1000dd9a4` / `dd5f4` 按输出色彩空间转回 RGB。
- 强度：按 dev+0x2c0（0x901c = 10）/ 10 在 look+0x1140 / +0x1154 表上插值（来自 0x7815 / 0x7816 = `0 32 108 … 646`，档位 10 取 32），再按 ISO 分段衰减（vtable+0xe8，节点 3200 / 12800 / 51200 / 409600）。
- 其余参数来自 0x794a–0x795e 和 0x7811–0x781a。
- 这些特征说明它是**多尺度低频色度降噪**（"大理石纹"彩色噪点）。本图是 ISO 100，强度只有满档的 5%，按理基本保持局部均值。
- 未移植的原因：多个分支依赖 `ZcARW` 解析后的内部状态（+0x148、+0x14c、+0x1b0、+0x22780/+0x22784 等）。要逐位验证，需要在模拟器里连同 ARW 解析器一起运行，或者完整移植约 3000 行代码。外部依赖只有 new/delete/memcpy/free，没有线程，所以整体模拟是可行的。

端到端（scale 8，Sony 前端，无拟合）：ST 3.56、FL2 3.74、FL3 3.89，外观差残差 1.02 / 0.97，与 §10.8 相同。§10.8 里约 2% 的增益缺口和暗部/中间调影调差**不来自** AreaComp、ToneCurve、ShadeCorrection 或 Effect。剩下的候选是 Marble、Sharpness、Spica 和 Demosaic 插值。

### 10.10 2% 增益缺口：0x7809 乘子（Ghidra 漏掉的一步）；插值保持均值；剩余误差来自镜头几何校正（2026-10-16，REA phase10）

**实际运行的插值任务**：
- 解码器的存储类型 `ZcARW+0x148` 来自原始 IFD 的 TIFF 标签 0x115 SamplesPerPixel，CFA 数据为 1。
- CFA 是 RGGB（look+0x84..0x90 = 0,1,1,2），不是 ZcTaskDemosaic 要求的 GRBG（1,0,2,1），所以构建器走 `FUN_1000b97a4`，插入 **ZcTaskITP**（vtable 0x1002c5688，处理函数 0x1000f95d0）。§10.8 里分析的 ZcTaskDemosaic（0x100138ac8）只用于 GRBG 传感器。
- **TrinityLPF** 要求存储类型 = 4 且 dev+0x2a4 = 1，这里**不运行**。

**ITP 的缩放**（vtable+0x60 = `FUN_1000f13bc`）：
- float32 计算 `(look[0x40]·2⁻¹⁵·gain) · 0.0625 · (raw − black)`，系数和 ZcTaskDemosaic 相同，但不截断。
- 插值是 G 平面加上 R−G、B−G 色差平面重建 R、B。之后限幅到 0..16383 并截断成 u16。
- 系数表 0x1003b96b8/96d4/96ed 由静态初始化函数 0x1000f9528 填写。

**缺口原因**：`FUN_10013c4b0` 在白平衡/色调步骤之后，还用 `d0 = (look[0x9d8]/256)·exp2(EV/300)` 乘每个增益（汇编 0x10013c6d4–0x10013c750）。Ghidra 的伪代码丢了这一步，所以 §10.8 的移植也漏了。
- look+0x9d8 = SR2SubIFD **0x7809 = 264**（解析代码 0x1000a740c；没有 0x7807 时默认 256）。
- 所以增益要乘 1.03125：R/G/B = 2735/1056/1460。§10.8 拟合出的最佳曝光 1.03 正是这个系数。

**用模拟器核对插值**：
- `memu.py` 是一个新的快速模拟器，只在库函数入口和 Sony 的池分配器（0x10011dc4c/0x10011dfa4）挂钩子，Sony 自己的图像对象代码真实运行。

- 结论：**插值保持均值**。代理改为"不截断的块平均 − 0.5"（`front_end_sony`，`sony_frontend.itp_scale`）。

### 10.11 镜头几何校正（GeoCorr）；Vatr 其实是 DRO；在模拟器中运行 Sony 的 ARW 解析器（2026-10-16，REA phase11）

**用模拟器打开 ARW**：
- `memu.py` 按 `dyld_info -fixups`（缓存在 `fixups.txt`）应用全部 rebase/bind。bind 指向按符号名分派的跳板，实现了 libc 的文件、字符串、数值转换和时间函数。文件只读。
- `open_arw.py` 调用 Sony 的 `FUN_1000d9690(&obj, FILE*, 0x1000)` → 构造 ZcARW（0x22788 字节，ctor 0x1000bbeb0）→ `FUN_1000a107c` 解析，用的是 `reference/` 下未被修改的原始 ARW。
- 解析出的字段：机型代码 +0xc = 0x197，格式代码 +0x50 = 0x3600，存储类型 +0x148 = 1，原始类型 +0xf8 = 4。look（vtable+0xe0）里的黑电平、0x7311、白平衡、0x9d8 = 264 等都和前几节的静态推断一致。
- 另写了 `raw_structure/sr2.py`：dcraw 同款 SR2 解密（0xc634 → 0x7200/0x7201/0x7221），可直接读取完整的 SR2SubIFD，不依赖 ExifTool。

**哪些阶段运行**：
- dev+0x238（0x8022）= 1 且存储类型 ≠ 4 → 插入 **Vatr**（处理函数 0x1000e65a4）。它**不是**镜头暗角校正，而是局部影调算子：对 Y 做 log2，从 render+0xc01c0 的低分辨率局部亮度图上插值，计算 `gain = exp2(((Y−局部)·强度 − Y) + 曲线(局部))`，三通道同乘。参数由 `FUN_1000fc3e0(…, 5, 0x8024 = 50, 0x802d = 50, …)` 设置。这就是 **DRO**（相机设置为 DRO Auto），**尚未移植**。
- look+0x12c0 ≠ 0 且 `aed68`（dev+0x278 = 0x8040 = −1，即自动）→ 插入 **GeoCorr**（处理函数 0x100140b34）。

**镜头结构 L = render+0x18**：由 `FUN_1000d58f0` 生成。0x7983 = (17, 16) 使 look+0x12fc/0x12fe ≠ −1，于是走模式 1（`FUN_1000d65a0` + `FUN_1000d69b4`）。
- **表**：G[i] = (float)(1 + 0x7984[i]·2⁻¹⁵)（19 个节点）。R、B = G·(1 + CA·2⁻²¹)，CA 分别取 0x7980 的前 16 和后 16 个值，下标大于 15 时取最后一个。畸变开关 dev+0x278，色差开关 dev+0x27c（0x900d）。
- **几何**：中心 = 解码器矩形的一半（3504, 2336）/ p5（导出时 p5 = 1）。节点间距 = 半对角线 / (k·p5)，k = 21.63（APS-C 为 14.2）× 0.69348127，即每节点约 1.44 mm 像高，本图为 280.75 px。
- **缩放 s**：在角落查 G 表。若 G < 1，则从短半边向外搜索第一个 `G(x)·y > hy` 的 y，s = (y − 0.5)/hy；否则从半对角线向内搜索。本图 s = **1.019050**（放大约 1.9% 填满画面）。
- **逐像素**：`r = sqrt(fma(dy,dy,dx·dx))`；`t = s·r/step`；`f = fma(t1−t0, t−⌊t⌋, t0)`（超出表时取最后一个节点）；`src = fma(f·((p+off)−c), s, c)`。然后双线性采样：`top = fma(X1−fx, v00, (fx−X0)·v01)`，`bot = fma(fx−X0, v11, (X1−fx)·v10)`，`v = fma(bot, fy−Y0, top·(Y1−fy))`，最后截断成 u16。
- **暗角**：解析器**不读取** 0x797d（ExifTool 显示的 VignettingCorrParams）。可能的阴影表 0x78a4–0x78ac 在本文件中全为 0。所以 Edit 不做镜头暗角校正；残差的径向分布也没有暗角规律。

**验证**：
- `verify_lens.py`：GeoCorr 在四角和中心共 4 个区域，输入为随机值和平滑图样，用 Sony 自己生成的镜头表，**4/4 逐位一致**。
- `verify_lens_tables.py`：`lens_struct_from_tags` 与 `FUN_1000d58f0` 比较，本图加 5 组改写过畸变/色差节点的合成用例，覆盖两种搜索分支，**6/6 逐位一致**（三张表和全部浮点字段）。

**端到端**（scale 8，无拟合；`front_end_sony` 在缩小网格上做 GeoCorr：每个块中心映射到源坐标后双线性采样，再减 0.5 的截断偏差）：

### 10.12 DRO（ZcTaskVatr）：双边网格局部影调，逐位移植；参考图未经过 DRO（2026-10-16，REA phase12）

**调用链**：`FUN_1000d52cc` 在存储类型 ≠ 4 时，先运行 DRO 子对象（render+0xc01c0）的构造函数 `0x1000fb758`，再调用 `FUN_1000fb9a4(…, 8, 6, 14)` 和 `FUN_1000fc3e0(…, 级别, dev+0x240, dev+0x244, dev+0x1e0)`。dev+0x238 = 1 时级别为 5；若 look+0x10f0 ≠ 0，级别改为 −1，即使用相机曲线。逐像素的处理在 Vatr（`0x1000e65a4`）中完成。

**分析部分**（输入是 Sony 解码器输出的整幅 raw 缓冲区，7168×5120）：
1. `FUN_1000fc734`：每 4 个像素取一个 RGGB 四元组，计算 `v = max(R−bR,0)·0.1495 + (max(G−bG,0) + max(B−bB,0))·0.057`，其中 G 取两个 G 的均值 >>1，黑电平来自 look+0x38/0x3a/0x3e = 512。然后查表得到 L = log2 v：表项 t[j] = log2f(8j)，按步长 8 线性插值，v ≥ 16384 时直接调用 log2f。表后紧跟一张 exp2 表，所以 t[2048] 实际读到的是 1.0，移植时原样保留。采样网格为 1792×1260，原点 (0, 40)。
2. `FUN_1000fd814`：每 16×15 个采样取均值（按顺序用 FMA 累加），得到 112×84 个子格；每 14×14 个子格组成一格，共 8×6 格。
3. 每格建 14 个 bin 的直方图：`bin = ⌊L·14/log2(8191)⌋`，每个子格加 1/196。`FUN_1000fda44` 再做 3×3 十字平滑（角、边、内部三种核，权重分别为 2/4、3/6、4/8）。之后按 bin 模糊：`W[j] = Σ h[k]·w[|j−k|]`，权重 w = 0.883, 0.605, 0.324, 0.137, 0.043, 0.012, 0.0039…（0x1002ecff8）；`S[j] = Σ k·h[k]·w + blend[j]·(W·j − ΣS)`，blend = 1, .75, .5, .25, 0×5, .25, .5, .75, 1, 1（0x1002ed088）。
4. 曲线（`FUN_1000fe258`）：由 10 个节点和 28 个三次 Bézier 控制值组成，在 `X_i = log2(8191)/104·i` 处采样 104 个点。**本 ARW 带有相机计算好的 DRO 曲线**：SR2 **0x781b**（节点）和 **0x781c**（控制值），均为 u16/1024。没有这两个标签时，使用 0x1002ed168 起的内置 0/5/10 三档表做插值。

**逐像素**（Vatr）：
- 输入 r, g, b 为 u16 >> 1；`Y = 2·(0.1495r + 0.2935g + 0.057b)`，L = log2 Y。
- 在 4 个最近格中心之间做双线性插值、在 bin 之间做线性插值（`FUN_1000fe7d4` + `FUN_1000e6388`），得到 W 和 S；`local = S/W`。
- `gain = exp2(((L − local)·强度 − L) + 曲线(local))`。dev+0x238 = 1 时强度为 1，所以 `gain = exp2(曲线(local) − local)`，只取决于局部亮度。
- `out = trunc(clamp(v·(1 + (gain−1)·1.0), 0, 16383)) << 1`，三通道同乘一个增益。输出的最低位总是 0。

**验证**（`verify_dro.py` → `verify_dro_report.json`）：
- 网格：用 Sony 解码器在模拟器中解出的真实 raw，加上渐变和随机两组合成 raw，比较采样、子格、直方图、平滑、W、S、曲线 7 个数组，**3×7 全部逐位一致**。
- Vatr：6 个位置（四角、中心、格边界、负坐标边距）× 随机/平滑两种输入，共 **12/12 个图块逐位一致**（每块 11520 个值，Sony 改动其中约 88%）。

为此 `memu.py` 新增了两类桩函数：`host_info` 报告 1 个 CPU，让 Sony 解码器（vtable+0x110）单线程运行，34–52 秒；float 版 libm（exp2f、log2f 等）在 double 中计算后舍入一次。模拟器解出的 raw 与 rawpy 的 raw_image **完全相同**。

**端到端**（`compare_reference.py --dro`，在缩小网格上用块中心坐标查网格，并补上截断偏差 −g/2−1）：

| | ST | FL2 | FL3 |
| --- | --- | --- | --- |
| 不加 DRO（默认） | **0.98** | **0.82** | **0.87** |
| 加 DRO（相机曲线） | 5.63 | 5.65 | 5.72 |

本图上 DRO 的增益中位数为：Y < 64 时 1.28，64–256 时 1.37，256–1024 时 1.13，1024–4096 时 0.93，高光 0.91。参考 TIFF 中**没有**这种暗部提升，而不加 DRO 时本实现已经略亮约 0.5 级。所以这三张参考图导出时 DRO 是关闭的，这与 §10.1 的记录一致；Edit 写入 ARW 的 0x8022 = 1 是之后保存的状态。因此 `front_end_sony` 默认 `dro=False`。§10.11 中暗部 +0.5～1 的偏差**不是** DRO 造成的。要复现"DRO 自动"的成片，用 `--dro`。产物：`montage_dro.png`（Sony | 不加 DRO | 加 DRO | log2 增益图）、`compare_report_dro_on.json`。

### 10.13 Sharpness 与 Spica：逐位移植；全分辨率裁块对照（2026-10-16，REA phase13）

**实际运行的版本**：`FUN_10004f5a8`（SIMD）和 `FUN_10014a1bc`（OpenCL）都返回 0，所以运行的是普通版 `ZcTaskSharpness`（处理函数 0x1000ef77c）和 `ZcTaskSpica`（0x100100b60）。Ghidra 不肯在 0x1000ef77c 建立函数，Sharpness 是直接按 otool 反汇编还原的。两者都只处理 YCC 的 Y 平面，原地修改。

**本图参数**：
- Edit 写回的设置 IFD：0x801a（dev+0x208，锐度）= 0；0x801b–0x801d（dev+0x20c/0x210/0x214）= 0；0x901d（dev+0x2c4）= 50。
- look+0x1060 = 1.7，obj+0x2277c = 1.0，ISO（vtable+0xe8）= 100。

**Sharpness**（ChromaSuppress 之后、YGamma 之前；区域先每边收缩 2）：
- H：沿 x 做 7 抽头二项式 (1,6,15,20,15,6,1)；C：对 H 沿 y 再做一次。逐源像素按顺序用 FMA 累加。
- L = 4Y + 上 + 下 + 左 + 右（整数）。
- `d = (Y − L/8) + s9·(L/8 − C/4096)`，s9 = 0.015·50 − 0.5 = 0.25。
- 硬阈值：|d| ≤ 25 时置 0；超过阈值的部分乘以 s0/s1 = 1。
- `Y' = clamp(Y + k·d, 0, 32767)`，k = 1.7·0.02·(0+100)·(50·0.02) = **3.4**。

**Spica**（YGamma 之后、YCC2RGB 之前；表来自 `Edit.app/Contents/Resources/srsettings0000.tbl`，SHA ef1dd637…，只读）：
- **表文件**：文件头 "SONY RAW SRPRM"，后接 (256, 100, 25, 10) 四个计数。随后是 256 个模式项（u16 系数组号, i8 dx, i8 dy），100×24×10 个 short 的系数源，以及 100×200 个 short（OpenCL 路径专用）。
- **系数**：加载时由权重 (2048, 0, …) 生成，每组 25 个抽头 = 原 short 值，中心抽头 = 512 − 其余之和。
- **模式 1 参数**：vtable+0x100 & 1 → 模式 1，参数块在 0x1002ecdb4。分类阈值 8；ISO 100 时第一遍强度 1.0、增益上限 4096/2048。
- **逐像素**：
  1. 十字 9 点普查：位 = (v − min ≥ (max−min)/2)；若第 9 位为 1，则把低 8 位取反；若 max − min < 8，归为第 0 类。
  2. 按模式查出系数组和方向步长 (dx, dy)，做 25 抽头菱形滤波 f（FMA 链）。
  3. `d = (f − 512Y)·1.0`；增益 = 2·min(g1(d/128), g2(max−min), g3((max+min)/2))，三个都是分段线性函数（`FUN_1001006d4`）。
  4. `t = trunc(d·增益/512²) + Y`，截到 0..16383。
  5. `Y' = Y + 0.5·0.0002·100·50·(t − Y) = Y + 0.5·(t − Y)`。滤波区域每边收缩 3，任务区域每边收缩 4。

**验证**（`verify_detail.py` → `verify_detail_report.json`）：

**端到端：全分辨率裁块**（`fullres_crops.py` → `render_output/fullres_crops_report.json`）：

### 10.14 Effect（BW / Sepia）：逐位移植；旧 SE 配置是全彩色的（2026-10-16，REA phase14）

**问题**：§10.9 只确认了参考图（ST/FL2/FL3）不走 Effect，没有移植。结果 `Look('Sepia')` 只跑了 SE 自己的 0x780f/YCC 参数，输出基本是彩色的：相机 RGB (300, 600, 1500) 的蓝色在 ST 下是 (713, 5461, 16383)，在旧 SE 下是 (1257, 7704, 16383)。v1.0.0 中的 `SonyA7M5-Look-SE.icc` 和 `SonyA7M5 Look SE.xmp` 因此是错的。BW 本来就是灰色，但 Effect 还会改变它的影调（见下）。

**定位**：构建器 `FUN_1000b85e0` 在 YCC2RGB / Marble 之后调用构造函数 `FUN_10013a978`，vtable 0x1002c6c70，Process 位于第 7 槽：**0x10013a9b8**。参数 `param_3[0]` = 解码器（vtable+0xe0 取外观结构），`param_3+0x44` = 输出色彩空间（0 = sRGB，1 = AdobeRGB），处理范围是 task+0x30..+0x3c 的矩形。

处理步骤，所有平面都是 0..16383 的 u16：

1. **转入工作空间**（BW、SE 都做）：mode 0 走 `FUN_1000dd41c`。先查 sRGB 解码表，再乘 Q13 矩阵 `[0x13b2 0xca2 −0x54; 0x2ec 0x1abd 599; 0x73 0x253 0x1d39]`，结果 asr 13 后截到 0..16383，最后查 γ = 2.19921875 的编码表。mode 1 走 `dd7cc`：输入改用 γ2.2 解码，矩阵不同。四张表由 `FUN_1000db9f4` 用 libm `powf` 懒加载生成，sRGB 编码和解码段里有 fmadd。
2. **BW（0x10）**：`R = G = B = min((2449R + 4809G + 934B) >> 13, 16383)`，即 BT.601。**之后不转回**，灰度值保持工作空间（γ2.2）的编码，直接当 sRGB 输出。所以 BW 的影调和"只跑 0x780f"时不同：中灰 14768 → 14718，暗部 506 → 856。
3. **Sepia（0x11）**：
   - `s = 2449R + 4809G + 934B`，`Y = s >> 13`。
   - `L = clamp(float(fmadd(B, 0.0722, fmadd(G, 0.7152, R·0.2126))), 0, 16383)`，这一步用 double 计算，即 BT.709。
   - 色调 (tR, tB) 在 `s>>19 ≤ 20`（Y < 1344）时乘以 `Y·0.00074404763`，在 `s ≥ 0x7482000` 时乘以 `fmadd(Y, −0.0007102273, 11.590909)`（即 (16320−Y)/1408）。
   - `R = trunc(tR + L)`，`B = trunc(tB + L)`，`G = trunc(L) − ((trunc(tR)·0x104c + trunc(tB)·0x636) asr 13)`，各自截到 0..16383。
   - 然后用 `dd5f4`（mode 0：γ2.2 解码、逆矩阵、sRGB 编码）或 `dd9a4`（mode 1）转回输出空间。
4. **色调来源**：tR = look+0x9a << 6，tB = look+0x98 << 6。`FUN_1000a31c8` 把 SR2SubIFD 的 **0x74c5**（int16[2] = B, R）读到这里，外观 IFD 里没有这个标签。条件是 look+0x2c = SonyModelID（MakerNote 0xb001）既不 < 3，也不属于 {0x100, 0x102..0x105}，否则改用内置值 (832, −1152)。**A7M5：SonyModelID = 407，0x74c5 = −15 14，即 tR = +896、tB = −960。** 两张参考 ARW 的值相同。

**验证**：`verify_effect.py` 在 Unicorn 中运行原始的 0x10013a9b8，包括建表和 4 个色彩空间函数，使用真实的 Sony 图像对象，`powf` 交给宿主 libm。覆盖 BW/SE、mode 0/1、机型 407/0x100/2、多组 0x74c5，以及随机、灰阶（跨越 1344 / 14912 阈值）、近灰、端点 4 类输入：**32/32 逐位一致**。端口位于 `sonylook/sony_effect.py`，`sony_render.Look.render` 在 YCC2RGB 之后调用，按 mode 0（sRGB 输出）处理。

**结果**：
- SE 下，蓝色 (300, 600, 1500) → (9885, 7787, 7158)，中灰 3000 → (16370, 14344, 13741)。
- 因为色调在 γ2.2 码值上近似恒定，转回 sRGB 后深暗部明显偏红（例如 (1327, 51, 0)）。这是 Edit 本身的行为。
- 重新生成了 `SonyA7M5-Look-SE.icc` / `-BW.icc` 和 `SonyA7M5 Look SE.xmp` / `BW.xmp`。现有配置都由 DSC03591.ARW 生成：用它重新生成 ST、FL2 与 v1.0.0 逐字节相同，说明其他外观不受影响。ACR 64³ 表相对外观链的误差：BW MAE 0.10，SE MAE 0.12（8 位）。
- 还没有和 Edit 导出的 SE/BW 图对照，因为没有这样的导出。

证据：`../rea/phase14/`（0x10013a978、0x10013a9b8、0x1000dd41c/5f4/7cc/9a4、0x1000db9f4、0x10013a3f4）。


### 10.15 RawNR：CFA 域降噪，逐位移植（2026-10-17，REA phase15）

**何时运行**：构建器 `FUN_1000b85e0` 在 dev+0x218（设置 0x801e）= 1 且解码器 vtable+0x100 ≠ 0 时插入。本图 CFA 为 RGGB，走非 SIMD 路径 `FUN_1000b9594` → ctor `0x1000e9acc`（vtable 0x1002c5208），Process 位于第 7 槽 **0x1000e9b48**，核心是 **0x1000e9d04**。同一开关下还有两个任务：`FUN_1000b83e8`（只在 vtable+0x100 和 +0xf0 的最低位都为 0 时插入，本机型不满足）和 YNR（dev+0x22c ≥ 1 才插入；dev+0x22c 由 `0x1000ddeb4` 从 dev+0x21c = 设置 0x8027 复制，本图为 0），所以这两个都**不运行**。

**参数**：解析器 0x1000a4adc 起，把 SR2 **0x78c0–0x78d7** 读入 look+0x1018–0x1098。其中 0x78cc–0x78ce（本图 480）会被截到 256；G 通道超出 256 的部分换算成 Sharpness 系数 look+0x1060 = 1 + (480−256)·0.003125 = **1.7**，这就是 §10.13 里 1.7 的来源。噪声表由 `FUN_1000d5ac0(render+0xd0, look)` 生成，三个滑块是 dev+0x21c / 0x220 / 0x224（设置 0x8027 / 0x8028 / 0x8029）：
- 阈值表 T[0x8000] 每通道一张：`(g·3·L1034 >> 8) + ((clamp(i, L102c, L1030) − L102c)·(3·L1038·g >> 8) >> 12)`，截到 0..0x3fff。其中 g = L103c·32·(0.03125 + s·0.0003125)。
- 混合表 W 为常数 512 + 5.12·s。
- 高频增益 = L1048（滑块 0x8028 为 0 时），限幅 = min(L1054, 8184)。
- 本图 T 为 3…16 DN，增益 256，限幅 1023。

**处理**（输入是含黑电平的 u16 原始 CFA，四个通道各自在同色格点上处理）：
1. 区域收缩 2 后，拆成高频 hp 和基底 b：
   - R/B：`hp = (12c − 对角±2 − 2·轴向±2) >> 4`
   - G：`hp = ((24c − 对角±2 − 2·轴向±2) − 3·对角±1) · 36 >> 10`，其中对角 ±1 是另一个 G。
   - `b = clamp(off + c − hp, 0, 0x7fff)`，off_R = L18 − L20、off_G = L18 − (L1c + L28)、off_B = L18 − L24。本图分别为 0、−512、0。
2. 区域再收缩 8 后，在间隔 4 像素的 5×5 同色格点上做 sigma 滤波：
   - 局部均值 m：R/B 取 3×3（间隔 4）·0x72 >> 10；G 取 ±4 范围内 25 个 G·0x29 >> 10。
   - `c' = (W·b₀ + (1024 − W)·m) >> 10`。
   - 满足 (c' − v)² ≤ T[b₀]² 的邻点和 b₀ 一起做整数平均。
3. 输出：
   - `out = clamp(clamp(gain·hp >> 8, ±lim) − off + avg, 0, 0x3fff)`。
   - 最终值 = `trunc(fmadd(out − raw, s, raw))`。s 按 ISO 取值：< 400 时为 0.4，≥ 1600 时为 1.0，中间线性插值，float32。

**验证**（`verify_rawnr.py` → `verify_rawnr_report.json`）：
- 在 Unicorn 中使用 Sony 自己的解析器和外观结构。
- 噪声表：8 组滑块设置 × 3 通道，**全部逐位一致**。
- Process：9 个图块，共 29 336 像素，**全部逐位一致**。图块包括随机、暗部噪声、边缘、3 块真实 RAW、偏移区域，以及 ISO 800 / 3200。Sony 改动了其中 54–91% 的像素。
- 端口：`sonylook/sony_rawnr.py`（`look_from_sr2`、`tables`、`rawnr`）。从标签生成的参数与模拟器中 Sony 解析出的 look 完全相同。

### 10.16 Marble：YCC 低频处理，逐位移植；ST 导出时运行，FL2/FL3 导出时没有运行（2026-10-17，REA phase15）

**何时运行**：(dev+0x218 = 1 且 look+0x109c ≠ 0) 或 dev+0x2c0（设置 0x901c）≠ 0。Process 为 **0x100126f0c**，子函数共 13 个。处理顺序：
1. `FUN_1001293ac` 用 dd41c 转入 γ2.2 工作空间，与 Effect 相同。
2. 转成 Marble 自己的 YCbCr：`Y = min((0xb44R + 0xdc3G + 0x271B) >> 11, 0xefff) + 0x1000`，`Cb = (−0x6abR − 0x964G + 0x1011B) >> 11`，`Cr = (0x1accR − 0x1ac0G − 9B) >> 11`，Cb、Cr 偏置 0x8000。
3. `FUN_10012672c`：区域宽高向上取整到 4 的倍数。色度横向两两平均（2:1）。右侧用第 x1 列补齐，底部用最后一行补齐。
4. **色度路径**（只在降噪开关 0x801e = 1 时运行）：
   - 先做块平均：look+0x109e = 1 时块为 8×8，否则 4×4，本图为 4×4。
   - `FUN_1001295b8` 在四周复制边缘各补 6。
   - 在 5×5（间隔 2）格点上做 sigma 滤波。阈值随亮度变化：`(c8 + (cc·Y + 0x80 >> 8))·(c0 …) >> 8`，再乘强度后截到 [0x100, 0x8000]。邻点必须同时满足 Cb、Cr、Y 三个差值条件，平均用倒数表 0x1002ed340。
   - `FUN_1001297f0` 做 3×3 二项平滑。
   - `FUN_100129af0` 双线性放大回半宽。权重表在 0x1002ed4a8–0x1002ed6a8；4×4 时下标会越过 8 项表，读到相邻的表，移植时照原样保留。同一列被后面的块覆盖。
   - 合并时，在 Cr 偏红且 Cb 接近中性的区域，把 Cr 拉回原值（护肤色）。
5. **亮度路径**（dev+0x2c0 ≠ 0）：
   - 8×8 块平均，5×5 sigma（阈值为 look+0x1174 = 96）。
   - `FUN_10012a250` 做 3×3 平滑，`FUN_10012a464` 做 8 倍双线性放大（double 运算，结果精确）。
   - `FUN_10012a804` 把细节 Y − 放大值按亮度相关的权重加回，中间调约 1/32。**输出量化到 10 位**（<< 6）。

6. `FUN_100126c58`：色度复制回全宽，**有效区域每边收缩 16**。
7. 色度按 f 与原值混合：`fmadd(新 − 原, f, 原)`。解码器 vtable+0xf0 = 0 时 f = 1.0，本图如此。然后 YCC → RGB，在收缩后的区域里用 dd5f4 转回 sRGB。

- 表中清晰度：ST、VV、NT、BW、SE、FL、IN、SH 以及 0x18 为 1，PT 为 0，VV2 为 8（所以默认 0x901c 分别是 10 / 0 / 80）；IN、SH 另有 3、6，表中其他参数都是 0。**表里没有 FL2（0x16）和 FL3（0x17）**，查表失败，所有默认值（包括清晰度）都是 0，Marble 只在降噪打开时才可能运行。这正好解释了上面的结果：ST 默认清晰度 10，Marble 运行；FL2/FL3 默认 0，Marble 不运行。在 Unicorn 里对本 ARW 调用解码器 vtable+0x188，得到的默认值与静态表一致。`sony_marble.clarity_default(look_id)` 给出这个默认值。

`sony_render.Look.render(..., marble=dict(look, dev, dec))` 可以在 YCC2RGB 之后运行 Marble。RawNR 用 `sony_rawnr.rawnr` 在 ITP 之前处理。两者都是空间处理，不进入 LUT，已发布的配置文件不受影响。

证据：`../rea/phase15/`（0x1000e9b48、0x1000e9d04、0x1000d5ac0、0x100126f0c 及 13 个子函数）。

### 10.17 与 Edit 4.1.00.03062 的对照（2026-10-17）

Sony 2026-05-14 发布了 4.1.00（新增 ILCE-7RM6、DRO Lv6–8）。从官方更新服务器下载 `IE410_2603a.dmg`（SHA `d7927e…`），只解包、不安装，取出 `Edit.app` 的 arm64 部分（`rea/targets/Edit41_arm64`，来源见 `identity41.json`）。对照脚本在 `../edit41_diff/`。

- **逐函数对照**：用 `LC_FUNCTION_STARTS` 切分函数，把跳转目标、页地址和数据引用替换成占位符后比较。4.0 的 10021 个函数里有 9683 个在 4.1 中完全相同。本文和移植代码引用的 131 个函数中，有 13 个在 4.1 里有改动；连同它们调用的函数（共 685 个）一起看，有改动的是 34 个。
- **只是结构体偏移变化**：解码器对象增大了约 0x888 字节（例如 +0x22774 → +0x22ffc，Marble 读取的 +0x22780 随之移动），文档对象 +0x78 → +0x80。Marble、Effect、锐化、镜头校正、DRO 参数读取和清晰度默认值查找这些函数，只是这些偏移变了，算法完全相同。
- **ARW 解析器**（0x1000a107c、0x1000a31c8）增加了新内容，推测是为了支持 7RM6。在 Unicorn 中分别用 4.0 和 4.1 的解析器打开本 ARW：外观结构体前 0x1200 字节（不计指针）完全相同，13 个外观编号的默认参数也完全相同。
- **外观默认参数表**（4.1 中位于 0x1002ec3fc）与 4.0 逐字节相同。**FL2/FL3 仍然不在表里**，默认清晰度仍为 0。界面字符串里的外观列表也没有变化。
- **DRO 曲线**（0x1000fe258）：内置强度表的插值范围从 0–99 扩展到 0–150，新增 100–150 两段表，对应发布说明中的 Lv6–8。原来 90–99 那一段的插值方式也改了。ARW 带有 0x781b/0x781c 时，用的是相机给出的曲线，不走这段代码，所以本图的 DRO 不受影响。
- **色温白平衡**（0x1000ae728，只在 dev+0x1e8 = 3 时运行）：4.1 多调用了两个新的辅助函数，具体行为没有验证。它只影响在 Edit 里按色温设置白平衡的情况，与外观颜色无关。
- **常量表**：本文和移植代码引用的 Edit 常量表中，能按内容检查的 25 张在 4.1 中都能逐字节找到。其余 19 张含指针或全零，无法这样检查。

结论：4.1 没有改动外观颜色链。已发布的配置文件、LUT 以及已移植的各阶段（Marble、RawNR、Effect、锐化、Spica、镜头校正）都继续适用于 4.1。
